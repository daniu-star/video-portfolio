# 《肉身审计局》v6：三维空间、身体行动与物理模拟深度迭代报告

**性质：** 可运行技术垂直切片（vertical slice）及阶段性技术方案。不是商业级3A成品，也不宣称达到了动捕、PBR写实或真正刚体模拟的行业标准。

**依据：** 基于 v5 第一人称问诊工程实际源码，对其中二维街景、平面人物、二维工厂采集动画及单纯点击式互动进行迭代。继续保留《肉身审计局》的三幕叙事和“陈俊良问诊室”，避免为了3D表现让人物重新变成算法管理员。

## 1. 重构目标与设计判断

v5已经解决了“患者为何可以修改系统参数”的视角错误，却保留了二维场景与点击按钮直接换章节的空间短板。现在要从“在网页中阅读一段被插画陪伴的聊天”转向“在一个可以行走、接近、绕过障碍的场景中经历事件”。但体量、文本和人机对话的可读性仍是主约束。**采用3D场景 + 2D原生聊天UI，而非所有内容都硬塞进3D。**

### 1.1 视觉与操作的三个层次

- **空间层：** 人、问诊机、建筑、障碍、工厂设备都有3D几何和坐标；地面有透视；人物走动，设备真实存在于空间中。
- **行为层：** WASD、方向键、地面点击、手机摇杆控制行动；有速度变化、边界碰撞、自动靠近。采集动作触发人物动作和数据传输反馈。
- **语义层：** 文字、聊天、合同、交易流水仍用可选择、可复制的HTML控件。它们解释行为，不与世界争夺视觉焦点。

### 1.2 不照搬所谓3A镜头

最佳参考并非高多边形堆砌，而是《Inside》《Firewatch》一类强调焦点、剪影、空间方向和情境反馈的设计理念。这里只借鉴设计原则，未使用其图像、角色、音效或代码。此次交付仍为自制程序化低多边形风格。

## 2. 实际完成的工程改变

| 子系统 | v5问题 | v6实际实现 | 明确边界 |
|---|---|---|---|
| 空间 | CSS二维建筑、人物剪影 | 三套独立的3D程序化场景，透视相机、深度与光照 | 几何较粗，没有高品质贴图/材质 |
| 角色 | 屏幕二维移动 | 3D人体部件、行走摆臂迈腿、接触阴影、工厂动作 | 非骨骼动画，无动捕/IK |
| 行走 | 只点击热点，人物预设平移 | WASD/方向键/点地面/手机摇杆、加速与阻尼 | 点地面为直线路径，没有复杂绕障寻路 |
| 碰撞 | 人物可穿过大量场景装饰 | 基于人物圆形碰撞体和矩形障碍的地面碰撞 | 没有三角网格精确碰撞或动态刚体 |
| 问诊机 | 平面热点 | 3D问诊终端、空间投影标签、接近互动、镜头式自动走近 | 未实现真正触摸屏材质/3D UI拾取 |
| 城乡 | 两幕常见背景差异不足 | 不同诊室外观、树木、围栏、材料和场景时间感 | 暂无实地建筑参考验证 |
| 工厂 | 2D动作人物+固定UI | 立体输送线、扫描工位、数据屏、运动中的货箱、捕获数据粒子 | 传送带是程序化运动，不是物理刚体输送 |
| 图形兼容 | 仅CSS原型 | WebGL1原生渲染 + 共享3D网格的CPU透视回退 + 旧二维最终回退 | 当前测试容器禁用了GPU，需真实硬件QA |
| 玩法 | 场景和对话割裂 | 3D动作桥接原有剧情：靠近机器才开启聊天，采集动作驱动身体反馈 | 聊天仍为脚本化多轮，非任意自由AI |
| 工程 | 逻辑结构集中 | 新增独立 `js/world3d.js` 与 `css/world3d.css`，保留 v5 引擎 | 需要下一阶段把人物动画/空间/物理再解耦 |

## 3. 场景逐幕重设计

### 3.1 第一幕——城市：以玩家的脚步进入问诊

**叙事意图：** 周远/林舟不是观众看到的抽象标签。他们已经站在同一条街上，向同一台设备靠近。玩家先感受路途、环境和空间交互，再进入暖白色问诊界面。

**空间构图：** 原点附近是可行走区域；问诊机位于场景右中部；建筑分为前景/中景/后景；街灯、站台、长椅、树池、路边车辆提供近大远小与遮挡基准。

**行动链：** 选角色→人物出现在街口→玩家沿地面行走→机器高亮→接近/按E或点击金色标记→自动步入机器前→网页聊天展开→询问症状/核对旧记录/查看摘要。

**反馈原则：** 点击金色标记必须有动作、距离变化和明确后果。为了避免低帧率让人误解，自动靠近的过场采用按真实时间插值约2.1秒，而自由WASD移动仍遵循加速/阻尼/碰撞。

**情境边界：** 职业不直接参与医学风险打分，角色差异仍由资料条件、说出的症状、既往信息和服务可达性解释。

### 3.2 第二幕——城乡：可见的空间差异，但不制造刻板印象

**叙事意图：** 玩家以赵伯或许阿姨身份进入一个具体的基层就诊环境，不是把城乡身份直接编码成健康缺陷。被漏记的句子仍必须通过对话纠正。

**空间构图：** 社区诊室和周边树木、围栏、通道，避免大量装饰把问诊机掩盖。设备形制延续第一幕，强调“同一种技术—不同记录条件”的对照。

**未解决：** 缺少连续就医路线、真正的出行耗时模拟、村医介入、双向病历流转与口音转写动态音频。应将这些作为具体可体验的后续支线，而不是多加环境贴图。

### 3.3 第三幕——工厂：让数据流看到它的生产现场

**叙事意图：** 阿玛拉的动作不是无来源的数据条目。她在工位上分拣、抬臂、弯腰；动作被采集，在工位设备和平台数据屏间显示流动。伊森调用同一份样本后，交易账本继续从上一视角留存。

**空间构图：** 箱体、传送带、AR扫描工位和平台数据屏之间有物理距离；数据粒子的传递方向与交易账本的逻辑一致。画面下方合同操作台仍维持二维控件，以保证易读。

**当前局限：** 箱子仅通过预置运动表达被搬运；还没有重量、力、抓取失败、疲劳累积、误操作、惯性、抓握点或人体关节约束。不能称之为真实的职业动作物理模拟。

## 4. 物理系统现状与进一步开发规格

### 4.1 当前：轻量运动学

角色平面坐标 x/z、速度 vx/vz，斜向输入归一化；输入时加速、松开时按指数阻尼减速；按轴分离尝试移动，阻挡时令当前轴速度归零。障碍采用半径约0.3m圆形角色碰撞体与AABB矩形碰撞。工厂中的货箱通过确定性时间运动模仿传送带。

**这可以验证：** “人不能直接穿过问诊机或部分设施”、“玩家可自己走到目的地”。

**这不能证明：** 人物与桌椅真正的刚体动力学、边缘滑动精度、物件堆叠稳定性、合理的脚掌落地、抓取物体时的力反馈。

### 4.2 下一阶段：有目标的真实物理，而非无差别上引擎

- 引入 Rapier 等物理层（需要正式依赖审批/许可核查），统一碰撞体、关节、速度约束和固定步长模拟。
- 站立、行走、停步、转身、弯腰、抬臂与举箱建立**人物状态机**，使用动画混合而非单次摆动。
- 必须加入地面接触点约束：站立时脚掌接地，转弯时脚步不会随镜头打滑。推荐两脚 IK、root motion 与动画曲线同步。
- “分拣”动作才需要真实物理箱体：抓取 → 施力 → 举起 → 放置 → 传送 → 扫描成功；任何一步失败须有可见反馈。
- 计算与展示疲劳只作为叙事里的可恢复状态，不暗示某种劳动者生理能力先天较差。
- 引入相机碰撞防穿模、可达点碰撞与狭窄通道脱困。

## 5. 顶尖游戏制作质感：建议验收标准，而非已实现成绩

| 维度 | 下一阶段目标 | 取证方式 |
|---|---|---|
| 运行性能 | 桌面中档设备目标60FPS，手机中档设备目标30FPS（参考目标） | P50/P95帧时长、渲染三角数、GPU/CPU耗时 |
| 操作响应 | 普通输入可见反馈目标<100ms，交互目标2步内可达 | 真人走查与自动记录 |
| 镜头 | 无突然跳帧、丢角色、穿墙、遮挡关键UI | 逐幕关键帧录屏对比 |
| 人物运动 | 无明显脚滑、手臂穿躯干、脚掌离地 | 跑动/转向/抓取5组动作镜头 |
| 物理 | 货箱接触、惯性、堆叠稳定、边界不穿透 | 高低帧率与慢放碰撞回放 |
| 视觉 | 统一PBR材质、动态/烘焙光照、接触阴影 | 白模、材质球、灯光对照 |
| 可玩性 | 新玩家不用看说明能发现问诊入口 | 真实盲测8–12人（建议样本，不是已执行） |
| 信息伦理 | 所有问诊结论均与实际输入一致、不把身份当风险因子 | 剧情矩阵与规则单测 |

## 6. 建议下一阶段 P0/P1/P2 backlog

**P0 / 必须先做：** 完成真正的WebGL GPU跨设备测试；手柄与触控走位可用性；验证3D问诊机热点在不同屏幕下不会遮挡人物；加入状态机清理异步回调；按游戏内UI流程跑通南北双角色；建立操作时长/重试/迷路点无隐私统计方案。

**P1 / 进入生产美术：** 人物骨架与材质、统一身高尺度、脚步/转身/抬手IK、箱体碰撞/抓取、材质库、真实光影、环境声音与空间化、过场镜头脚本、遮挡消隐。

**P2 / 深化叙事：** 城乡真实转诊路径、回访电话与时间成本、工厂合同实际议价机制、数据集复制与退出权、最终证据图的可交互追溯。

## 7. 《build-3d-game-rooms》门禁执行情况

本轮已阅读游戏空间规范、设计原则、流程及验收模板，按照该规范建立城市、城乡与工厂三套 `docs/room-review/` 原型说明，包括房间目的、尺寸、英雄交互、相机、通路、拟制道具清单、开口与阶段复核状态。

**实际状态：** Function gate = 待审批；Form gate = 未启动；Runtime gate = 待生产端正式批准。我们仅制作**自有程序化浏览器技术原型**，没有使用付费 Meshy、没有提交外部平台生成任务、没有 Blender 最终资产、没有官方平台发布。不存在已获人工批准的房间审查结果。

需特别补齐：正交平面图、完整入口与开口遮挡关系图、3D美术参考contact sheet、明确的人体资产审批、封闭几何壳和布尔门窗、正式相机与各视角渲染检查、灯光/纹理tier，以及真实GPU上的WebGL渲染性能与交互测试。

## 8. 测试与交付真实性说明

- Node `13/13`规则与几何测试通过：原7个剧情/账本测试+6个3D几何/边界/障碍测试。
- 使用浏览器软件三维投影模式，在1440×900桌面视口自动走通选角、3D城市、自动接近、聊天、城乡并进入工厂；在390×844模拟手机视口验证选角、3D城市、自动接近、聊天与城乡场景。测试路径没有未处理的JavaScript异常，移动端工厂完整闭环与实际操作系统触屏手势仍待复测。
- 自动化系统禁止浏览器直接导航本地文件，因此采用页面及JS/CSS内容注入的方式测试；这不能代替用户本机双击打开验证。
- 自动化浏览器禁止创建 WebGL 上下文，因此**没有真实GPU WebGL画质和FPS的直接证据**。本次截图来自同一三维几何的CPU软件投影版本，不是外部生成的静态海报，也不是商业3D美术最终稿。
- 没有真实零基础用户样本和行为指标。没有开展性能压测，也没有完成A/B对照。

## 9. 交付文件与打开方式

工程目录根文件 `index.html` 可以解压后直接双击；本项目另生成同目录 `肉身审计局_v6_单文件试玩.html`（全量JS/CSS及四张文献截图内嵌）。两个入口都无需在线CDN。最便捷的分发方式是直接发送单文件HTML；最适合开发迭代的是 ZIP 内多文件工程。

**最终判断：** v6解决了从二维舞台到三维可行走空间的基础结构问题，但它仍然是低多边形可玩技术切片。若目标是市面顶尖设计质感，下一步应重点投资**人物动作可信性、交互后果与光影材质统一**，而不是简单提高场景复杂度。
